# SCALE UPGRADE CHECKLIST (10,000+ CONCURRENT USERS)

The following upgrades are recommended to scale the backend signaling and media plane to 10k+ concurrent users.

1. CORE CODE LOGIC FIXES
[ ] Fix Ghost Participants: Create a background worker in `RoomPresenceService` to clean up inactive/crashed participants using Redis heartbeats, resolving the crash-vulnerability bug.
[ ] Optimize Pub/Sub Channels: Change `RoomEventHub` to subscribe dynamically to room-specific channels (`kzys:room:events:{roomId}`) instead of the single global channel.
[ ] Optimize Search: Replace Redis `HashScan` in `SearchParticipantsAsync` with PostgreSQL indexed queries.

2. DATABASE & CACHE INFRASTRUCTURE
[ ] DB Migration: Migrate from SQLite to a highly available PostgreSQL cluster.
[ ] DB Pool: Deploy PgBouncer in front of PostgreSQL to manage thousands of active socket connections.
[ ] Redis HA: Move from standalone Redis to Redis Sentinel or cloud-managed Redis (AWS ElastiCache / GCP Memorystore) with at least 2GB of RAM.

3. MEDIA SFU SCALING (LIVEKIT)
[ ] Dedicated Media Nodes: Deploy compute-optimized server nodes (e.g. AWS `c5.2xlarge` or GCP `c2-standard-8`).
[ ] Autoscaling: Configure Horizontal Pod Autoscaling (HPA) for both the signaling controllers and LiveKit nodes.
[ ] CDN Egress: For large view-only rooms (>2,000 users), configure LiveKit Egress to stream via RTMP/HLS to a CDN (e.g. Cloudflare Stream / AWS IVS).

4. NETWORK & OPERATING SYSTEM CONFIG
[ ] File Descriptors: Raise OS open file limits (`ulimit -n`) to 65535 on Kubernetes nodes and Nginx proxies.
[ ] WebSocket Tuning: Turn off or minimize WebSocket compression on ASP.NET Core signaling pods to save CPU.
[ ] Session Affinity: Enable IP or Cookie-based sticky sessions on Nginx to route participants of the same room to the same signaling replica where possible.

## 10,000 USER CAPACITY ANALYSIS

### Why the system cannot handle 10,000 users in its current state:
1. **SQLite Database Bottleneck**: The default SQLite database locks writing threads when multiple concurrent writes occur. Thousands of active signaling requests will cause crashes and timeout errors.
2. **Global Redis Event Multiplexing**: Routing all server room events through a single Redis Pub/Sub channel (`kzys:room:events`) will exhaust server CPU resources as every signaling instance must parse every message globally.
3. **Grace Leave Vulnerability**: The local in-memory grace disconnect timers (`RoomPresenceService`) will drop during server restarts/crashes, leaving orphaned participants stuck in the Redis active list.
4. **Single-Node Media Caps**: LiveKit pins each room to a single media node. Standard compute nodes saturate at ~150 video publishers or ~3,000 simultaneous audio/video viewers per room.

### Requirements to achieve 10,000+ scaling:
* **Database**: Move to PostgreSQL with PgBouncer connection pooling.
* **Pub/Sub**: Partition events into room-specific Redis channels (`kzys:room:events:{roomId}`).
* **Cleanup Worker**: Implement a persistent background cron worker checking participant heartbeats.
* **Large Room Streaming**: Use **LiveKit Egress** to stream massive view-only webinar rooms (>2,000 users) out to a scalable RTMP/HLS CDN.
